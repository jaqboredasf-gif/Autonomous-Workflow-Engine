# PCC workflow hardening gap matrix

Audited against the merged Phase A + Phase B baseline (`bd33adc`) on
2026-08-10. Phase A history remains frozen: this phase changes neither its
snapshot contract nor its append-only write path.

| Screen / action | Expected behavior | Current behavior | Gap | Severity | Proposed smallest fix |
|---|---|---|---|---|---|
| Sign in / role landing | Each employee lands in the workspace their role can use. | Role-based landing and guarded routes already exist and are covered by web acceptance. | None. | — | Keep existing behavior. |
| New request prerequisites | A worker can tell whether PCC is ready before filling a request. | With no delivery location the form cannot submit; the reason is only discovered at the bottom of the form. | Avoidable setup dead end. | P1 | Show a prominent setup message before the form; point administrators to Administration and other users to their PCC admin. |
| Material autocomplete | Typing a completed material shows tenant-scoped evidence and selecting it prefills reusable fields on a new request. | Phase B endpoint and control already do this; free text remains available. | Complete lifecycle acceptance does not yet prove the evidence reappears after this run completes. | P1 test gap | Extend the lifecycle acceptance scenario through completion and the next autocomplete query. |
| Submit / queue | Submit creates a new request and immediately places it in workshop review. | `DRAFT → SUBMITTED → PENDING_WORKSHOP_REVIEW` is one unit of work and the queue remains visible. | None. | — | Keep existing behavior. |
| Workshop review | Authorized approver edits purchasing-only fields, chooses a vendor, and decides; requester fields remain immutable. | Existing ReviewForm and server authorization enforce the separation and show observed versus configured vendor evidence distinctly. | An empty vendor directory is only exposed by an unusable picker / failed approval. | P1 | Explain the required admin setup on the review screen and disable approval until a vendor exists. |
| PO generation | Approved request produces one idempotent PO and stored document. | Existing service, route, and tests cover this. | Action failures on the detail page are silently discarded. | P1 | Return a visible action error on the request page; preserve idempotence. |
| Vendor email workflow | A human edits, reviews, opens/sends, records sent evidence, then records the order placed. | Draft lifecycle exists, but request detail offers **Mark ordered** as soon as the draft is created; a premature click silently fails. After `SENT`, the email page has no direct next action. | Misleading action and dead-end handoff. | P1 | Offer Mark ordered only when a vendor draft is `SENT`, show action errors, and add the post-send action on the email page. Do not add mail transport. |
| Order / tracking | A purchaser records the real placement and office can add tracking. | Existing status, permission, audit, and queue support are present. | Covered by the email handoff gap above. | P1 | Use the existing `markOrderPlaced` path after sent evidence. |
| Receiving entry | A receiver must record at least one real quantity. | Submitting every line as zero creates an empty receipt and can move an order to Partially Received. | False operational evidence. | P1 | Reject a receipt with no received, damaged, backordered, or written-off quantity before any provider write. |
| Damaged receiving | “Received” is the physical quantity; “damaged” is the unusable subset. A 10-unit delivery with 2 damaged resolves 10 ordered units and adds 8 usable units. | Progress adds received and damaged as separate fulfillment, while inventory also subtracts damaged. Entering 10 received / 2 damaged can therefore close 12 units against 10. | Incorrect completion and immutable-history evidence. | P0 | Count damaged as a subset of received in local and Supabase progress/RPC arithmetic; retain the existing inventory `+received - damaged` evidence. Add a forward migration but do not apply it to hosted Supabase. |
| Backordered / written off | Backordered remains open; written off resolves the quantity with evidence. | Existing quantity fields and progress rules already behave this way. | None beyond explicit regression coverage. | — | Pin behavior in the lifecycle acceptance test. |
| Foreman / jobsite confirmation | Assigned field user can confirm only their job; unrelated field and request-only users are refused. | Assignment-scoped receiving, Deliveries workspace, and server-side denials already exist. | Full workflow test should retain both positive and negative controls. | P1 test gap | Exercise assigned foreman receipt and protected-transition denials in the consolidated scenario. |
| Completion | Only a fully resolved `RECEIVED` request can become terminal `COMPLETED`. | Existing transition guard and immutable completion trigger enforce this. | Detail action failure would currently be silent. | P1 | Surface the server result; do not change completion or history semantics. |
| Immutable history / next request | Completion writes once; future search reads evidence without mutating it. | Phase A/B implementation and focused suites cover the pieces separately. | No single acceptance scenario proves the closed loop. | P1 test gap | Assert history capture, immutable-write refusal, and next-request suggestion in one lifecycle scenario. |
| Queues / dashboard | Active work never disappears; received work is visible until completed. | Existing dashboard and queue stage model cover the lifecycle. | None. | — | Keep existing behavior. |
| Mobile / tablet | Request and receiving controls work one-handed without horizontal workflow dead ends. | Both forms are mobile-first with large controls and a sticky receiving confirmation bar. | No P0/P1 gap found in static audit. | P2 | Defer visual polish; manually verify phone-width layout. |
| Spanish UI | Use localized labels where a catalogue already exists. | Stable status message keys exist, but the application has no end-to-end UI message catalogue; most screens are explicitly documented as English-only. | Broad translation would be a new architecture phase. | P2 | Do not introduce an i18n subsystem in hardening; retain stable status keys for a later scoped phase. |

## Selected implementation scope

Only the P0/P1 rows above are in scope: receiving correctness, non-empty
receipt validation, email-to-order handoff and action feedback, setup guidance,
and a consolidated lifecycle acceptance scenario. No autonomous decision,
external mail send, hosted migration, or Phase A history redesign is included.
